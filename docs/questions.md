# 現場の健全性診断 — 質問と採点（v0.2）

## 対象

- **v1：エンジニア本人向け**（参画中の現場を自己診断する）
- 次：管理者向け（同じ問いを管理者の視点の文言で聞き、メンバーとの認識のずれを出す）→ 末尾の「管理者向けの構想」

## 回答と採点

- 対象：**今いる現場**で起きていることについて答える（期間は区切らない）
- 3択：よくある／たまにある／ない
- 通常の問い（⚠）：よくある = 0点、たまにある = 1点、ない = 2点
- 逆転の問い（✅ 良い行動を聞く）：よくある = 2点、たまにある = 1点、ない = 0点
- **項目別スコア** = カテゴリの得点 ÷ 満点 × 100（四捨五入）
- **総合スコア** = 全20問の得点 ÷ 40 × 100（四捨五入）

### 総合スコアのラベル

| スコア  | ラベル |
| ------- | ------ |
| 80〜100 | 健全   |
| 60〜79  | 注意   |
| 40〜59  | 要警戒 |
| 0〜39   | 危険   |

## 質問（20問）

### A. 残業文化（4問）

1. ⚠ 遅くまで働いた人にだけ、リアクションや称賛がつくことがある
2. ⚠ 定時で帰るときに、気まずさを感じたり理由を説明したくなったりすることがある
3. ⚠ 遅れが出たとき、スコープや期限の見直しより先に「残業で取り戻す」話になる
4. ⚠ 見積もりやスケジュールが、残業する前提で組まれている

### B. 変更管理（3問）

5. ⚠ 作業に必要なアカウントや環境が、事前の告知なしに変更・削除されることがある
6. ⚠ 仕様や優先度が、理由の説明なく変更されることがある
7. ⚠ 環境や前提が整っていないまま、作業の開始日や期限が決められることがある

### C. 扱いの公正さ（3問）

8. ⚠ 作業の件数やスピードを、中身を見ずに他の人と比べられることがある
9. ⚠ 実際の作業を確認せずに「簡単そう」「もう少しできるはず」と言われることがある
10. ⚠ 業務委託や派遣などの立場を理由に、提案や懸念を聞いてもらえないことがある

### D. 時間への配慮（3問）

11. ⚠ 作業中に、こちらの都合を確認せずに通話や打ち合わせに呼ばれることがある
12. ⚠ 会議が予定の時間を過ぎても、主催者が止めずに続くことがある
13. ⚠ 勤務時間外のチャットに、すぐ返信することを期待される

### E. 心理的安全性（4問）

14. ⚠ 問題を報告すると、内容を受け止める前に、質問の仕方やタイミングを指摘されることがある
15. ⚠ 質問すると、面倒そうな反応や遠回しな非難が返ってくることがある
16. ⚠ 障害やミスのあと、原因よりも「誰がやったか」が話の中心になる
17. ⚠ リーダーや管理者の判断でチームの作業が止まったり遅れたりしても、謝罪の一言もないことがある

### F. 人への関心（3問・すべて逆転）

18. ✅ リーダーや上司から、仕事の負荷や体調について聞かれることがある
19. ✅ チームの会話で、メンバーの働きやすさや成長が話題になることがある
20. ✅ 工夫や頑張りが、件数や数字以外の形でも認められることがある

## 結果ページ

1. **総合スコア**（0〜100）とラベル
2. **項目別スコア**（6本の横棒）
3. **優先して見る項目**：スコアが最も低いカテゴリ（同点なら A→F の順）。スコアが80以上ならこの欄は出さない
   - 根拠：そのカテゴリで点数を落とした回答（⚠「よくある／たまにある」、✅「ない／たまにある」）を一覧で出す
   - 本人が取れる行動（下表）
4. シェア：X への投稿ボタン（総合スコアとラベルを本文に入れる）。OGP 画像はラベルごとに1枚
5. 誘導：job-fit-agent（次の現場探し）、商談質問リスト（準備中）
6. 注意書き：企業名は入力・保存しない。回答はブラウザの外に送らない

### 本人が取れる行動（エンジニア向け）

| カテゴリ     | 行動                                                                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 残業文化     | この現場では、遅くまで残ること自体が評価されやすくなっています。個人の頑張りでは変わりにくいので、自分が働く時間の上限を先に決めておきましょう。実際に働いた時間を記録しておくと、負担を説明するときの根拠になります。                                                     |
| 変更管理     | アカウントや仕様の変更があったら、日時・内容・影響をメモに残しましょう。遅れの理由を説明するときや、負担について相談するときに、自分を守る材料になります。                                                                                                                 |
| 扱いの公正さ | 進捗を報告するときは、件数だけでなく、作業の難しさと詰まっている理由も一緒に伝えましょう。比べられる前に、比べ方の前提をそろえておくためです。提案や懸念は、チャットなど記録が残る場所で伝えておきましょう。聞き入れられなくても、自分が指摘していたことを後から示せます。 |
| 時間への配慮 | 集中する時間をカレンダーに入れて見えるようにしましょう。会議は終了時刻の5分前に、次の予定があることを伝えておくと抜けやすくなります。                                                                                                                                      |
| 心理的安全性 | 報告や質問は、口頭ではなくチャットやチケットなど記録が残る場所で行いましょう。「いつ伝えたか」が残っていれば、後から責任を押し付けられにくくなります。                                                                                                                     |
| 人への関心   | 現場から気にかけてもらうことは期待しにくい状態です。自分の負荷や体調を自分で記録し、限界が来る前に、信頼できる人に相談したり、環境を変えることを考えたりしましょう。                                                                                                       |

## 管理者向けの構想（v2）

- 質問は「問いのID」と「文言」を分けて持つ。同じIDに対して、エンジニア向けと管理者向けの文言をそれぞれ用意する
  - 例（14）エンジニア向け：問題を報告すると、内容を受け止める前に、質問の仕方やタイミングを指摘されることがある
  - 例（14）管理者向け：問題の報告に対して、内容を受け止める前に、質問の仕方やタイミングを指摘することがある
- カテゴリと採点のルールは共通にする
- 結果のアドバイスだけ相手によって変える（管理者向けは改善の優先順位と打ち手）
- 将来：同じ現場のメンバーと管理者の結果を比べて、認識のずれを出す
